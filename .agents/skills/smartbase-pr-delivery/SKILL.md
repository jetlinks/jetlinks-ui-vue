# SmartBase PR 交付

按项目规范填写 PR 描述。模板以 [`.github/pull_request_template.md`](../../../.github/pull_request_template.md) 为准，**保持标题、顺序和空行不变**。

复杂交付流程（分支策略、commit 规范、测试门禁）配合 `$jetlinks-delivery` 使用；本技能专注 PR 描述填写与发起。

## Workflow

1. 确认当前分支、目标 base 分支和改动范围（`git status`、`git diff`、`git log`）。
2. 运行相关测试并收集**数字证据**（通过数、失败数、跳过数、覆盖率）。
3. 判断「设计与测试目标」各子项适用性；不适用的写「不适用」并附一句依据，不要留空。
4. 按模板逐节填写，将占位示例替换为本次改动的真实内容。
5. 创建 PR 前确认任务状态：未完成用 draft，已完成且证据齐全再 ready for review。
6. 使用 `gh pr create` 时，将填好的描述通过 HEREDOC 传入 `--body`。

## 填写规则

### 目的

- 第一句写能力变化（修复 / 优化 / 新增）。
- 第二句写解决的问题或业务目标。

### 核心变动

- 按模块或目录列出，说明行为变化与新增约束。
- 只写事实，不写「优化了代码」这类空泛描述。

### 设计与测试目标

- 较大后端改动必须有设计稿路径；无设计稿时说明原因。
- 数据权限、链路追踪、MBean 等子项：涉及则写结论，不涉及则写「不适用：…」。
- 前端改动：数据权限 / TraceHolder / MBean 通常不适用；设计稿可为 UI 线框或交互说明路径。

### 测试结果

- **后端**：命令示例 `mvn -pl xxx -am test`。
- **前端**：命令示例 `pnpm test`、`pnpm build` 或项目实际脚本。
- 必须给出具体数字；不能仅写「测试通过」。
- 集成测试触发条件：数据库、消息、事件、协议、跨模块边界、外部依赖或启动装配。

### 文档同步情况

- README 仅在长期总览变化时更新。
- 测试证据放 PR / CI，不单独新建测试报告文档。

### 风险与说明

- 每项必须有内容；无风险时写「无」或「不涉及」并说明依据。
- 兼容性与发布边界：说明是否影响已发布逻辑或持久化数据。

## 禁止事项

- 不要修改模板标题、章节顺序或合并章节。
- 不要用「已测试」「已优化」替代具体数据。
- 不要在证据缺失时将 PR 标为 ready for merge。
- 不要直推 `master` / `main` / 版本集成分支。

## 输出格式

交付请求按以下顺序输出：

1. 建议的 commit message（`type(scope): summary`）
2. 完整 PR 描述（与模板结构一致）
3. `gh pr create` 命令（如适用）
4. 剩余阻塞项或 draft 原因（如有）

## 示例触发

```text
使用 $smartbase-pr-delivery 根据当前改动整理 PR 描述并生成 gh pr create 命令。
```
