# 代码复用思考指南

> **目标**：新增代码前先判断——仓库里是不是已经有了。

---

## 问题本质

重复代码是最常见的一致性问题来源。

当你复制粘贴或重新写一段“近似逻辑”时，通常会出现：

- 一个地方修 bug，其他地方漏修
- 同一业务行为在不同页面表现不一致
- 代码越改越散，后续维护成本上升

---

## 编写前检查

### Step 1：先搜索

```bash
# 搜函数名 / 关键词
grep -r "functionName" .
grep -r "keyword" .
```

### Step 2：问自己 4 个问题

| 问题 | 如果答案是“是” |
|------|----------------|
| 是否已有相近函数？ | 优先复用或扩展 |
| 是否已有相同模式？ | 跟随现有模式实现 |
| 是否适合抽为公共能力？ | 放入合适的共享位置 |
| 是否在复制别处代码？ | 先停下，考虑抽象 |

---

## 常见重复模式

### 模式 1：复制校验逻辑

- ❌ 反模式：每个页面都写一份相同校验函数
- ✅ 建议：提取到公共工具，统一维护

### 模式 2：高度相似组件

- ❌ 反模式：新建一个和旧组件 80% 相同的组件
- ✅ 建议：通过 props / slots / variants 扩展已有组件

### 模式 3：常量散落多处

- ❌ 反模式：同一个常量在多个文件重复定义
- ✅ 建议：单一来源维护，其他地方 import

---

## 何时应抽象？

建议抽象：

- 同一逻辑出现 3 次及以上
- 逻辑复杂、出错概率高
- 多人/多模块都会使用

暂不抽象：

- 只使用一次
- 一行且可读性很好
- 抽象后反而增加理解成本

---

## 批量改动后检查

做完多文件修改后，至少再做一次：

1. 回顾：是否都改到了
2. 检索：是否仍有漏网旧逻辑
3. 判断：是否值得收敛为公共实现
